# 笔记输出模板与范例

本文件供 `ppt-basic-deduction` 写作前参考：上半部分是结构模板，下半部分是一段缩微范例，展示"理解型笔记"的质地。

## 结构模板

```markdown
# <主题：一个能概括全篇的标题，不带任何文件名/课程号>

> 一句话总览：<这份材料最核心的结论或主张，一句话说完。>

## 要点速览

1. **<要点 1 断言>**：<一两句展开>
2. **<要点 2 断言>**：<一两句展开>
3. ...

## 1. <断言式章节标题：本节结论>

<正文：先通俗解释概念，再给准确定义；有因果必写为什么。>

<Mermaid / 表格 / ASCII 还原的图>

<图后一句话：这张图说明的关系/读法。>

## 2. <断言式章节标题>

...

## 附：术语表（可选）

| 术语 | 一句话解释 |
|---|---|
| ... | ... |

## 作者的构思与不足

**作者为什么这样写：**

- **目标与受众**：<想让谁记住什么、做什么；材料性质是教学/汇报/说服/销售>
- **叙事策略**：<开头的钩子、顺序与详略、收回落点各自服务于什么效果>
- **取舍逻辑**：<被放大的、被一笔带过的、被省略的，及其暴露的价值观>

**这个构思的不足：**

- **客观限制**：<篇幅/受众/场合约束导致的妥协；无则略去本条>
- **认知盲区**：<缺失视角、未覆盖反例、过时前提、未回答的显然问题>
- **有意隐藏**：<被淡化的不利信息、缺失的对等对比、未声明的假设；写明判断依据>

> 每条判断附依据；纯推测处标注"（推测）"；不足处尽量补一句"如果补全会是什么样"。
```

## 缩微范例

以下示范同一段内容的"坏写法"（镜像 PPT）与"好写法"（演绎笔记）。

### 坏写法（禁止）

```markdown
### 幻灯片 5：缓存架构图
如 PPT 第 5 页图所示，系统分为接入层、缓存层、存储层。
[图片: slide5.png]
幻灯片 6 提到缓存命中率 99.2%。
```

问题：有元数据、有图片引用、图没有还原、"提到"是转录口吻而非理解口吻。

### 好写法（目标）

```markdown
## 写入路径绕过缓存，是三 layered 架构保证一致性的关键

系统自上而下分为接入层、缓存层、存储层。关键设计在于：**读走缓存、写穿存储**——
写入不更新缓存，而是直接落库并让缓存失效，由下一次读请求重新加载。
这样宁可牺牲一次读延迟，也避免"缓存与库双写"这一经典不一致根源。

\`\`\`mermaid
flowchart TD
    Client[客户端] --> GW[接入层: 鉴权/路由]
    GW -->|读请求| Cache{缓存层}
    Cache -->|命中| Client
    Cache -->|未命中| DB[(存储层)]
    DB -->|回源加载| Cache
    GW -->|写请求: 直接落库| DB
    DB -.->|失效通知| Cache
\`\`\`

读这条链路时抓住一点：写路径（实线向下）从不经过缓存的"更新"分支，
缓存只接受"失效"这一种来自写路径的影响——一致性正是靠这个单向约束换来的。
实测该方案下缓存命中率为 99.2%，未命中时的回源成本被证明可以接受。
```

注意好写法的特征：标题是结论；术语就地解释；"为什么"（避免双写不一致）写在"是什么"之后；图用 Mermaid 保真还原并配读法说明；数据（99.2%）自然嵌入论证而非孤立转录。

### 收尾章节范例（作者的构思与不足）

```markdown
## 作者的构思与不足

**作者为什么这样写：** 这份材料的受众是准备做技术选型的团队负责人，目标是说服他们
采用该缓存方案。因此叙事上先渲染"双写不一致"的事故场景制造紧迫感，再让自家方案
作为唯一解法登场；99.2% 的命中率被放在最显眼的位置，而未命中时的回源延迟只用
一句"可以接受"带过——这个详略分配说明作者最希望读者记住的是命中率数字。

**这个构思的不足：**

- **认知盲区**：全文未讨论缓存节点本身宕机的降级策略，高可用视角缺失；如果补全，
  应有一节说明熔断与多级缓存兜底。
- **有意隐藏**：命中率 99.2% 没有给出测试的流量规模与时长，且全程未与竞品方案做
  对等对比（推测：该数字来自理想环境下的压测，对选型决策的参考价值有限）。
```

注意收尾章节的写法：分析的是"设计"而非攻击作者；每条不足都带依据或标注推测；可提及"作者/原作"但仍无页码文件名。
